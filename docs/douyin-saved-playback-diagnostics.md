# 抖音本地收藏播放诊断

用于检验“本地收藏超过两周后提示视频不存在”这一反馈。只检查腕上 RSS 本地收藏，不读取抖音账号的线上收藏列表。

## 采集内容

每次打开抖音收藏视频，`DouyinSavedPlayback` 日志会把这些观测关联到同一个进程内编号：

- 收藏类型，以及收藏至今的天数。时间直接取本地收藏记录；收藏与稍后再看的时间分别处理，不能用视频发布时间替代。
- `<7 天`、`7–<14 天`、`14–<30 天`、`≥30 天` 和时间未知五组。14 天整归入第三组；时间缺失、无效或在未来均记未知。
- 保存的媒体地址中是否有明确的过期参数，以及参数指示的实际过期时间是否已到。没有参数时记未知，不根据收藏时间推断 URL 有效期。
- 初次解析来自网络还是短期缓存、HTTP 状态、API 数字状态、响应是否缺少 `aweme_detail`。缓存命中或宿主未提供状态时，HTTP 记 0、API 状态记 -1。
- 本次解析与保存的媒体地址是否不同。若只有分享页而没有旧媒体地址，变化状态记未知。
- 播放器实际错误枚举，以及宿主确实提供时的 HTTP 状态；不从任意错误文本猜测状态码。
- 强制刷新是否发生、地址是否变化、刷新后是否真正出首帧；返回播放 URL 不能作为恢复成功的依据。
- 离开播放页时记录结果。一次打开及其所有重试只计一次；中途退出、取消或刷新后尚未出帧的观测单列为未定。

该诊断复用既有播放和重试请求。读取本地收藏元数据不会新增抖音请求，也不会为了采集额外尝试旧 CDN 地址。详细日志存放于已有本地 `app_log.txt`，受现有日志大小上限和导出机制管理。新增日志不含视频/账号标识、标题、URL、Cookie、响应正文或任意错误文本。工作人员端另接入下述最小问题事件上传。

## 工作人员端图表

后台可观测中心新增“抖音本地收藏 · 播放问题”，支持 **1 日（最近 24 小时）**和 **7 日（最近 7 天）**切换。时间范围按问题实际发生时间计算，趋势标签为 UTC+8。

| 必需指标 | 已确认口径与展示 |
|---|---|
| 用户遇到问题的次数 | 一次打开本地收藏视频首次遇到解析/播放器失败计 1 次；自动、手动重试和恢复后再次失败均不重复累计；重新打开可以再计 1 次。显示总数与逐时/逐日趋势。 |
| 遇到问题的用户数 | 后端从有效登录会话取得账号，周期内 `COUNT(DISTINCT user_id)`，同账号跨设备去重；周期人数不能用逐时/逐日人数相加。 |
| 收藏到发病时长 | 同一账号、同一收藏实例的全历史最早观测失败时间减收藏时间；显示中位数、平均数及 `<1 天`、`1–<7 天`、`7–<14 天`、`14–<30 天`、`≥30 天`、未知分布。重复问题不会重置首次发病。 |

时长指标的周期样本为“首次观测失败落在该周期”的收藏；更早已发病、在本周期再次失败的收藏仍贡献次数与人数，但不重新贡献首次发病时长。未知/未来收藏时间保留未知，不填 0 天，也不进入均值和中位数。上线前已经发生但未被采到的问题无法倒推。

RSS 详情播放器和抖音详情播放器均传递同一个打开诊断对象。详情初次刷新失败但原地址仍可播放时，仅记录解析线索；只有播放失败或完全无法进入播放器才生成问题事件。非收藏、仅稍后再看、取消/过期回调均不进入此统计。

事件先持久化到本地账号隔离队列，上传失败保留，应用启动、账号变化、回到前台和新问题会触发补传。队列最多 1000 条，保存可补传的最近 31 天；容量满会记录固定诊断而非淘汰尚可上报的事件。因此图表代表登录用户**成功上报**的问题，并非全部安装用户的完整故障总量。

每次问题使用随机 UUID，服务端 `(user_id,event_id)` 唯一键防重传重复计数。收藏实例使用账号、后端地址、视频 ID、收藏时间的 SHA-256 摘要；视频 ID、标题、地址、Cookie、手机号不会随事件上传。账号身份来自认证，不接受客户端提供 `userId`。

实现包括客户端 `src/telemetry/saved-playback.ts`、同级 `WatchRSS_Backend` 的迁移 `0103_douyin_saved_playback_issues.sql`、事件接口和后台聚合接口。接口、数据库与验证命令见 [后端说明](https://github.com/LightningLion-Studio/WatchRSS_Backend/blob/main/docs/douyin-saved-playback.md)。上线顺序：应用数据库迁移、发布后台/只读代理，再发布包含新采集逻辑的手表版本；本次没有操作线上环境。

## 生成报告

导出包含新记录的 `app_log.txt` 后运行：

```sh
bun scripts/douyin-saved-report.ts app_log.txt douyin-saved-report.html
```

原网速报表也会自动增加收藏诊断区域：

```sh
bun scripts/video-speed-report.ts app_log.txt video-speed-report.html
```

报告包含各收藏时长组的打开次数、首帧成功次数、未出帧并最终失败次数、失败率和未定次数；并直接比较满 14 天与不足 14 天两组。失败率分母为成功出首帧或具有最终失败记录的打开；不包含未定和中途退出。成功出帧之后的失败会出现在错误线索中，不会被误算为无法开始播放。

同一日志的完全重复行会去重；应用重启后进程内编号从 1 重新开始时，以新 `open` 记录开始新的打开。日志轮转丢失开头时，无法关联的后续记录单列，不制造收藏时长或打开记录。

## 如何回答反馈

| 观测 | 能支持的判断 |
|---|---|
| 满 14 天组失败率与较新收藏不同 | 检查是否有时长相关性；不能据此证明两周自动失效 |
| 旧媒体地址已明确过期，重新解析后可播 | 支持旧地址无法继续使用、需要重新解析这一解释 |
| 播放失败，强制刷新后换地址且出首帧 | 证明同一条目在刷新后可以播放；仍不能排除网络或编码变化等共同因素 |
| 强制刷新得到 URL，但没有首帧 | 不记为恢复成功 |
| HTTP 200，缺少 `aweme_detail` | 详情没有返回可解析的视频字段；不能单独宣称视频已删除 |
| 非零 API 状态、登录/限流/挑战错误 | 先检查接口访问问题，而非把所有失败归为“视频不存在” |
| 媒体地址 HTTP 404/410 或 `source_expired` | 当前媒体地址不可用，不等于抖音上的原视频永久消失 |

实际是否删除、私密或账号不可见，仍需平台明确的状态证据；当前代码不会把未知数字状态码解释为删除。收藏历史时间未知的记录不会归入“两周以上”。
