# Foreground synchronization and background IO completion

The native foreground policy has been ported to `src/sync/foreground.ts`: all eligibility facts are required; brief pauses retain an idle listener for 2.5 seconds; accepted transfers survive backgrounding; failed accepts retry after 500 ms; media ownership has a 30 second handoff grace. Listener cleanup completes before another listener starts. Disposal cancels timers, stops the listener and releases its lease.

Oracle: `WatchBluetoothForegroundSyncManager.kt` and `BluetoothTransferScreenOnController.kt` in the original Android application. The controller has six focused tests for eligibility, pause/resume, transfer completion, retry/disposal, media lease renewal, delayed listener cleanup and unexpected factory failure (some tests cover multiple conditions). The main application now instantiates this controller through the production lifecycle/display/audio binding; see [application integration and real paired-phone evidence](sync-application-foreground.md). Full action dispatch and IP integration remain pending.

A required runtime fix accompanies this policy. Previously the Android host stopped visual frames at lifecycle `background`; queued service results could then remain unprocessed. The new additive C entry point `pod_runtime_pump_services` invokes the optional framework service pump and drains Promise jobs without invoking the frame function, ticking layout, or committing a draw snapshot. Android calls it on lifecycle/IO completion while suspended and drains the resulting service effects. It does not run an idle polling timer. Foreground frame behavior and background frame suspension remain intact.

The isolated `tests/runtime-foreground` watch application opens its own RFCOMM test listener, waits to enter the background, then completes SQL, timer and cancellation operations. Actual recorded result: all operations passed; frame callback count stayed at 2249 before and after the background work. This proves guest/host completion delivery in a stopped activity, not a paired-phone transfer or immunity to OS process termination. The fixture uses a separate test UUID, modifies only its own KV result and performs a read-only SQL query.

Evidence: `artifacts/foreground-guest-kv.json`, `foreground-controller-test.log`, `foreground-framework-tests.log`, `foreground-runtime-tests.log`, and `foreground-receipt.json`. No main application library synchronization is advertised as complete. Physical visual acceptance remains outstanding.
