# Verified article receive and reader persistence

`SyncArticleReceiver.receive` verifies one manifest-selected, nondeleted article body, publishes any large content files, then commits its channel, article, original content, previews, body metadata, reading position and saved states in one SQLite transaction. Corrupt or unavailable metadata-only bodies are rejected before article mutation. A failed database transaction retains the previous article; newly published unreferenced files may remain for later garbage collection. This entry point does not accept whole-article deletions, select manifest requests, maintain peer cursors or send an ACK.

The incoming body is checked through the existing native-compatible codec. Plain text and HTML longer than 50,000 UTF-16 units are externalized through the checked native-format writer. The repository and original-content service can hydrate these file markers for ordinary HTML readers; imported text keeps the chunk reader path. Ordinary HTML hydration and the codec still allocate whole strings in JavaScript, so large-book memory and performance are not qualified by these tests.

Merge policy follows native `upsertSyncedArticleItem`: nonblank incoming HTML wins over text; blank bodies retain existing body content. Metadata/title fields are applied by the receiver because native selection happens in the manifest coordinator. A new body hash, later reading timestamp, authoritative mode, or forward progress with both timestamps zero can select an incoming position. Normal merges OR the read flag and retain the maximum reading timestamp, even when a changed body selects an older position. Authoritative merges replace the read flag and timestamp. Incoming safe numeric values are checked; Kotlin Long values outside JavaScript's exact range are rejected rather than silently rounded.

`SqlReadingProgressStore` is now the production reader service. It migrates old KV state with INSERT OR IGNORE and projects the winning progress to the article in the same transaction. KV entries remain intact for rollback; once a SQL state exists, a later KV read cannot overwrite it. Remote-selected positions clear old local layout anchors; preserved local positions retain them. Local saves are serialized per article, follow the native float progress threshold and byte-position rounding, and do not reject an intentional local action merely because the remote clock is ahead. The reader UI uses this service through its existing load/save boundary.

The receiving coordinator must initialize its own persisted UUID identity and select the article before calling the receiver. Existing RSS identities without a resolved native mapping and body metadata cannot be assumed to support partial-body reuse. Metadata hashes for outgoing native manifests, complete deletion/media lifecycle, change-log/peer cursor updates, multi-frame collection and transport acknowledgement remain outstanding. Blank-body insertion currently does not populate an original-content cache entry; the article's fallback excerpt is stored, but this edge of original-mode behavior remains to be reconciled.

## Validation

`capture-article-merge.py` executes the native upsert method verbatim with the native data classes (Room annotations removed) and DAO/metadata/externalization/size helper doubles. Its 48 cases qualify entity merge decisions; they do not validate Room, filesystem or metadata hash generation. The receiver's Bun SQLite tests compare body, original body, progress, byte position, position hash, timestamp and read state against those results. Additional tests cover corruption rejection, full transaction rollback, missing files, metadata-only reuse, legacy anchors, source channel behavior, local float threshold and a future remote clock.

The existing `dev.podjs.tests.syncstate` verification package now executes these 48 native cases with production QuickJS, SQLite, body codec and file writer, together with the earlier 144 saved-state cases. Its large-body case writes 54,000 UTF-16 units, reads the file through the repository, preserves a later local save, checks rollback/corruption, migrates an old KV anchor, observes remote progress through the reader store, and checks local save ordering and a future remote clock. These are data/reader-service checks, not physical scrolling or visual acceptance.

See `artifacts/article-receive-receipt.json`, the recorded device result and corresponding build/test logs for installed identities, source hashes and validation results. A pre-upgrade copy of the production database, KV and body files is kept locally in the private `article-receive-userdata-before.tar` backup.
