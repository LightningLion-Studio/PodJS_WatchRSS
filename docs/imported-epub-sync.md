# Phone-imported EPUB chapters to PodJS watch

On 2026-09-25, isolated physical tests imported a two-chapter EPUB through the phone companion's production `PhoneCompanionRepository.importLocalContent`, then used its production `PhoneBluetoothSyncManager` and the paired RFCOMM connection to replace an empty PodJS watch fixture library. The phone repository used an in-memory Room database and an owned temporary file directory; neither installed production library received test chapters. A second run made the first chapter large enough for the phone's file-backed HTML store and used a fresh empty watch fixture.

The phone importer reported one book source named `示例书名` and two chapters in spine order, `第一章` then `第二章`. It identified the isolated watch app before reusing the persistent socket. The phone reported two articles sent and the watch acknowledged application. The watch held one book channel and two chapter articles with `https://watchrss.local/import-epub/.../chapter/0001-...` and `0002-...` identities. Reading the chapters through production `services.getArticle` returned the expected Chinese chapter text. In the large-chapter run, the first chapter's 130,000 additional Chinese characters were stored as a phone file marker, transferred and materialized as a watch file marker, then hydrated by the reader service; its `rawContent` length was 130,043 characters and contained the complete sequence. Both corrected fixture runs reported `passed`, with two watch articles and three successful listener actions; SQLite quick check was `ok` and foreign-key check returned no rows. An initial attempt applied the transfer but failed only the fixture's incorrect URL assertion; the fixture was corrected and retested in a fresh empty app.

The final large-chapter isolated watch APK SHA-256 was `d9d020adc76b45cb50cb4cd5f88bc83e08fb19632340d57d5e101c769623a8c9`; the phone test APK SHA-256 was `3abcbf0a1161bba3761136d09e45b764b56fceab531b117151c8ed3839d3f349`. Sources are `tests/runtime-phone-epub-peer` and `Android_WatchRSS_Phone/app/src/androidTest/java/com/lightningstudio/watchrss/phone/connection/bluetooth/PhonePodjsImportedEpubDeviceTest.kt`. The watch database snapshots are `.codex-tmp/watch-source-replace-20260925/epub-guest-final.sqlite` and `epub-long-guest-final.sqlite`.

The production ReaderScreen was then mounted in the isolated watch fixture with the imported 130,000-character chapter. An initial capture saw only the first body line because the renderer had not finished drawing. A second OWW242 instrumentation run waited five seconds after the first visible frame and captured the TextureView directly: [EPUB reader screenshot](../artifacts/epub-reader-large-delayed.png) shows the title and multiple consecutive body lines. The test passed 1/1 without synthetic touch input. This also exposed a `RangeError: Accessibility text exceeds 4096 UTF-8 bytes` for an unbroken CJK paragraph: when the native wrap helper returned no breakpoints, `content-layout.ts` emitted the whole 2,000-character run as one accessibility line. Its fallback now measures and wraps on code-point boundaries, capped at 1,024 code points per line. The regression test, all 708 application tests and TypeScript checking pass.

The fixed main watch APK was installed with SHA-256 `f4c6b07369562256b6c9a33813200aa369ce229cc0d95d0768bf63aa6ce0a3ad`, matching the device APK. The main watch database still held 16 channels, 6006 articles, 7 memo notes, 105 synced body caches, 6 saved states, and 2 peer states; quick check was `ok` and foreign-key check returned no rows. The owned EPUB watch guest, its instrumentation package, and the phone test package were removed; the main watch app was resumed. This proves the two-chapter repository, transport, storage and reader-service path and a visible first page of one 130,000-character chapter. It does not prove the phone file picker, visible chapter list, EPUB navigation links and images, full-book scale or scrolling performance, physical touch, or final visual parity.
