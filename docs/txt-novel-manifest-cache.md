# Imported TXT chapter manifest cache

On 2026-09-25, the 5,378-chapter isolated snapshot left `article_sync_content` and `article_sync_encoding_cache` empty. The imported chapter's stable sync ID is a hash of its URL, while its SQL `dedup_key` is a chapter key or URL. The later body-source lookup searched for `dedup_key = sync ID`, found no row, and could not publish the derived body cache. Repeating the snapshot would therefore compress the same chapters again.

The local manifest now resolves a `https://watchrss.local/import-*` chapter back to the row already selected **when that row carries a native `syncBodyHash`**. It reuses the body encoding calculated for that same row, then publishes its local encoding metadata after the existing revision and source-row checks. This condition preserves the native reference behavior for imported rows without a native body hash. The main watch library has native body hashes for all 5,378 TXT chapters; the change does not require rewriting their source rows.

The isolated OWW242 package `dev.podjs.tests.manifestcache` tested 100 synthetic chapters. It first generated body hashes, staged them as native hashes, then generated and persisted a new manifest. The final generation used the persisted cache. Results from the package KV: first 12,135 ms / 100 encodes, cache publication 9,712 ms / 100 encodes, cached generation 4,387 ms / **0 encodes**. The second and third manifests matched exactly; the database contained 100 body-cache and 100 local-encoding rows, with `quick_check=ok` and no foreign-key errors. This validates persistence and reuse on the device, not full-library repeated-snapshot timing.

A subsequent isolated OWW242 test used five **real** chapters copied from the main watch database: two from the 2,583-chapter book and one from each of the other three TXT-novel channels. The selected rows included each channel's longer chapters; the test copy retained their original-content chunks and native hashes, then removed unrelated rows. All five production encodings matched their stored native body hashes exactly. The first manifest encoded five bodies in 1,833 ms and published five cache rows; the second encoded zero bodies in 625 ms and had identical manifest content. The guest database passed SQLite checks. This sample supports hash compatibility across the four books, but does not prove every one of their 5,378 chapters matches.

The test then used an isolated copy of **all 5,378 real chapters**, four channels, their native hashes, original-content chunks and five external content files. The first copied database omitted the external files and produced only 5,373 cache rows; this exposed a fixture omission, not missing files in the main app. An initial tar transfer of the five files also truncated their 136-character content-addressed names on the device. Each file was subsequently copied under its complete marker name and its content SHA-256 was checked against that name. On the resumed isolated run, all 5,378 manifest bodies were available. Every encoded body hash and content hash matched the corresponding native hash, with zero mismatches. The database contained 5,378 body-cache and 5,378 local-encoding rows; `quick_check=ok` and foreign-key checks were clear.

That resumed complete manifest took 309,590 ms and encoded the five bodies that had not yet been cached. A fresh second manifest took 222,262 ms, encoded **zero** bodies and matched the first manifest exactly. These timings are for an already partly cached first pass followed by a fully cached pass; they do not measure a clean end-to-end first cache build. The cached pass remains slow enough to require further optimization.

The application passed 712 tests and TypeScript type checking. The native manifest fixture still matches its first and repeated reference manifests. The production APK [watchrss-podjs-imported-manifest-cache.apk](../artifacts/watchrss-podjs-imported-manifest-cache.apk) was installed on OWW242; both archive and installed `base.apk` have SHA-256 `df91e98c5c02d2fbfa3ff67d02027728fb2f2e0832ab6ca7f385c115c767004f`. It reached the first texture frame. The guest package was removed and the main app restarted. Before/after SQL rows matched for all 32 main database tables; the database file hash changed, but `quick_check=ok`, foreign-key checks and counts of 16 channels, 6,006 articles, 7 memo notes, 105 existing body caches, 6 saved states and 2 peers remained valid.

The clean first real 5,378-chapter cache-build duration and full phone-to-watch Bluetooth transfer remain unverified. The completed full-library repeated snapshot took about 3.7 minutes, so reuse alone does not make large-library synchronization fast. All guest packages and temporary device database copies were removed, the main app resumed, and all 32 main database tables retained exactly the same rows with valid SQLite checks.
