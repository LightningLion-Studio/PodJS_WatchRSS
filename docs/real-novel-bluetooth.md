# Real 5,378-chapter Bluetooth replacement trials, 2026-09-25

An isolated OWW242 PodJS package (`dev.podjs.tests.realnovelpeer`) listened with a copy of the real four-book library: 5,378 chapters, their original body hashes, and the five external text files. The phone instrumentation used the production RFCOMM manager and an in-memory Room database. It checked the watch identity before requesting `WATCH_TO_PHONE_REPLACE`; neither production library was a transfer target.

The identity probe succeeded and reused its persistent session. The watch returned the cursor after 226,081 ms and all 5,378 manifest entries in six frames. The phone requested 5,378 bodies (5,410 chunks) in a 1,070,543-byte article request at 08:44:17 UTC. It received no first article response by 09:04:05 UTC. The 1,800,000-ms library timeout closed the socket, and phone instrumentation failed with `java.io.IOException: bt socket closed, read return: -1` while reading `libraryResponse`. The watch process remained alive and CPU busy; its fixture KV was still `running/listening`. Thus this trial proves probe, cursor, and manifest exchange, but **does not prove any chapter body transfer or phone import**.

The repository used a five-minute wall-clock expiry for a cached sync snapshot even when the library revision had not changed. This trial exceeded that interval before the body request, forcing a redundant full snapshot in `exportRequested`. The cache now remains valid while its revision matches and is released after export; a six-minute cache regression test passes. This removes one known repeated scan, but the per-chapter body materialization, response framing, Bluetooth throughput, and full end-to-end completion still need measurement. The failed fixture was force-stopped. The isolated package remains installed for a controlled retest.

The repaired application passed 712 app tests, TypeScript checking, Android build and packaging. `artifacts/watchrss-podjs-session-snapshot.apk` was installed on OWW242; its archive and installed `base.apk` have the same SHA-256, `dfb3b37b8828f6f69d0aa12191ca24bab8e1666c3524a423850660809d6f53b3`. After launch, all 32 production database tables matched their pre-install row counts and content digests; `quick_check=ok` and foreign-key errors were zero. The production PodJS activity was restored. This install does not constitute a passed full Bluetooth test.

An isolated export-only profiler reused the same 5,378-chapter copy to separate CPU stages from radio time. With the old response builder, cursor/snapshot took 231,540 ms, the unchanged window 2,622 ms and body materialization 515,752 ms; response framing still had not finished after 11 minutes, so that run was stopped. Changing only the JSON size calculator did not finish framing within five minutes and was also stopped. With direct JSON byte counting and bounded Base64 string assembly together, the watch completed 5,378 encodes and produced 134 protocol frames: cursor 225,268 ms, window 2,484 ms, body materialization 513,702 ms, frames 333,915 ms, total 1,075,558 ms. This is an isolated CPU/serialization measurement, **not** a successful Bluetooth transfer or phone import. The 134 frames fit the phone's 256-frame protocol limit. Final frame validation was then changed to reuse exact per-item byte counts instead of rescanning every complete frame; its full-library device timing remains unmeasured.

The final size-validation change passed native outgoing-frame fixtures and the application suite (714 tests), TypeScript checking and Android build/package. The production APK is [watchrss-podjs-serialization.apk](../artifacts/watchrss-podjs-serialization.apk), SHA-256 `33fb42e5c6fc4f02cfecaa7b9f72703ad45f09fd11708e712dd07602bb6e541a`; the installed OWW242 `base.apk` has the same hash and launched without a PodJS/AndroidRuntime error. All 32 production database tables matched pre-install row counts and content digests; `quick_check=ok`, foreign-key errors zero. The isolated package was stopped and the production activity restarted. The full Bluetooth replacement must still be rerun and the phone's 30-minute timeout assessed against transfer time; none of these CPU timings imply a passed phone import.

The second real Bluetooth trial reused the same isolated watch copy and phone in-memory Room test. At 10:38:47 UTC it established the authenticated session; cursor took 232,825 ms, the six-frame manifest and article request completed, and all **134/134 body frames arrived** by 11:08:03 UTC. The phone sent `received` ACK, but the fixed 1,800,000-ms exchange timeout fired at 11:08:47 before the 5,378 articles were applied. The `applied` failure ACK could not be written to the closed socket; instrumentation failed with the timeout, and the watch fixture reported `Sync connection closed`. Thus complete body transfer is verified, while phone commit and digest are still unverified.

The phone companion now grants a 60-minute overall timeout to force-full or authoritative replacement sync, retaining the 30-minute limit for normal incremental sync. Its debug app/test build passed; the installed phone app and archived `Android_WatchRSS_Phone/artifacts/watchrss-phone-full-sync-timeout-debug.apk` share SHA-256 `cc8cf6410f06cd39539d4605daf3f55790bc50968f6ebd2fd621adb30823981d`. After upgrade, all 17 production phone DB tables retained the same row counts and content digests, with valid integrity and foreign keys. This only removes the proven deadline; it does not assert that the third transfer or phone import has passed.

The third real Bluetooth trial **passed end to end**. The same isolated OWW242 copy and production RFCOMM manager started probing at 11:12:23 UTC and started sync at 11:12:29. The cursor returned at 11:16:16, all six manifest frames arrived, and the phone requested all 5,378 bodies at 11:17:58. It received all 134/134 body frames by 11:43:01 and sent the `received` ACK. At 11:44:07 the phone reported `received=5378`, `merged=5378`, `sourcesReceived=4`, and `sourcesMerged=4`; it then completed the persistent session. The watch fixture reported `state=passed`, `articles=5378`, `caches=5378`, `actions=3`, and `elapsedMs=1929797`. Phone instrumentation passed in 1,943.354 seconds and independently checked all 5,378 nonblank bodies: the digest over sorted article IDs, content hashes, and SHA-256 of full UTF-8 body text was `70c5778b3eaa6db81a65867c22a73e5eefaae96960e1ecbbe53b5bd676e3b8c8`, identical to the source copy. This proves full watch-to-phone replacement into an isolated in-memory phone library; it does not test a production-library replacement, the reverse direction at this scale, or physical UI/gesture parity.

Afterward the isolated watch package and phone test package were uninstalled, and the production watch and phone activities were restored. The production watch's 32 SQLite tables had unchanged row counts and content digests; `quick_check=ok` and foreign-key errors were zero. The production phone's on-disk database file hash was unchanged. Its WAL held two article metadata changes logged at 11:11:06 and 11:11:32 UTC, before this trial began; its article count remained 10,744 and no change-log entry was added during the trial. The production phone snapshot passed `quick_check` and had no foreign-key errors. The isolated watch copy differed from its pre-trial snapshot only in `sync_peer_state`, as expected from the successful session.

## Reverse direction: phone to watch

A separate phone test database was made from a local snapshot of the phone library and limited to the same four real TXT-novel sources and 5,378 chapters. It contained 51,597,047 UTF-8 body bytes; the independent digest over sorted article IDs, source content hashes, and body SHA-256 values was `72e87ea2e799e4d7239200b3b84049f9d800826b8eac935de58d2d6112acdf63`. The production phone database was not opened as the sync target. An isolated OWW242 package (`dev.podjs.tests.realnovelreverse`) started with an empty article library and a separately checked watch identity.

The phone started the full `PHONE_TO_WATCH_REPLACE` exchange at 11:54:31 UTC. The watch requested all 5,378 bodies after six manifest frames, and the phone sent 87/87 article frames by 12:02:08. The watch then applied the articles and prepared its final response; at 12:42:03 the phone reported `sent=5378`, `received=0`, and a completed persistent session. Phone instrumentation passed in 2,899.558 seconds; the watch fixture reported `state=passed`, 5,378 articles, four channels, 5,378 body caches, and `elapsedMs=2913758`. A stable copy of the completed watch SQLite database passed `quick_check` with zero foreign-key errors. Joining `sync_article_ids` to cached bodies yielded exactly the source 5,378 IDs, with **zero** title, URL, or UTF-8 body mismatches. The body count and digest matched the independent phone fixture, including all 51,597,047 body bytes.

The old receiver did unnecessary work at the end: `exportRequested([])` built a fresh full-library snapshot even though the phone requested no watch bodies. An early return now releases the session cache without querying or encoding the library. Its focused repository regression, all 715 app tests, and TypeScript checking passed. On the completed 5,378-article isolated watch library, this empty export returned zero articles in `0 ms` at `Date.now()` resolution. This microbenchmark demonstrates removal of that unnecessary scan; it is not a second full Bluetooth timing measurement. The rebuilt production APK is [watchrss-podjs-empty-export.apk](../artifacts/watchrss-podjs-empty-export.apk), SHA-256 `d70455d8c4654b84006c4438f505a07b7f1c3b7121b2bf2b0cd70b82f3f85c30`, matching the installed OWW242 `base.apk` hash.

After the reverse trial, the isolated watch package and phone test package were uninstalled and the 66 MB private phone fixture file removed. Both production activities were restored. All 32 production watch tables still matched the pre-trial row counts and content digests, with `quick_check=ok` and zero foreign-key errors. The production phone's on-disk DB file hash was unchanged; its live snapshot still had 10,744 articles and 16 sources, passed `quick_check`, and had zero foreign-key errors. It recorded ordinary article-metadata updates when the production app was restarted; it was never used as this trial's replacement target. Physical UI and gesture parity remain for user acceptance.
